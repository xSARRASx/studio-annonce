# Parcours photo publié le 1er octobre 2026

Le site public `studioannonce.fr` ouvre maintenant la vraie vitrine, avec les exemples, tarifs, aide et blog sur leurs URL publiques. L'ancienne démonstration reste accessible pour les brouillons historiques, mais aucun appel à l'action public n'y mène. Les boutons des exemples conduisent aux pages correspondantes.

Les appels à l'action « Préparer ma photo offerte » sur l'accueil, les tarifs et l'aide mènent à `/connexion/?suite=photo`. Après vérification du code, le client arrive à `/app/#nouvelle`, l'écran d'import photo ; si le profil doit être complété, l'intention est conservée et l'import s'ouvre après enregistrement. Dans le compte connecté et dans l'aperçu mobile Expo, les encarts de photo offerte ouvrent directement l'import. Le mot « préparer » est intentionnel : aucune image n'est générée tant que le service IA n'est pas disponible.

La demande de retouche est enregistrée avec la photo sur le compte serveur. Elle se retrouve sur le site et dans l'aperçu mobile connecté. L'import de la photo et de sa première demande est atomique. La page photo distingue l'enregistrement du brouillon de la génération ; un écran d'attente avec conseils s'affichera pendant une génération réelle sur le site et sur mobile. Il n'affiche ni pourcentage ni délai fabriqué.

Pour les nouveaux imports, la photo source est orientée correctement, bornée à 2 048 pixels sur le plus grand côté puis encodée en JPEG progressif qualité 88 ; les vignettes et aperçus restent en WebP. Les fichiers déjà enregistrés ne sont pas modifiés. Le dossier de photos de production était vide au contrôle du 1er octobre, tandis que les anciennes sauvegardes du site occupaient environ 514 Mo. Une tentative de sauvegarde intégrale supplémentaire a échoué sur la limite de stockage ; son archive incomplète, créée pendant cette tentative, a été retirée. Avant les modifications suivantes, une sauvegarde ciblée des pages a été conservée dans `~/sauvegardes-studio/frontend-cta-targets-20261001.tar.gz`, et l'ancien module image dans `~/sauvegardes-studio/images-avant-optimisation-20261001.py`. Aucune ancienne sauvegarde ni donnée client n'a été supprimée.

Publication sur le compte N0C `vzbbtadpbm` : export Next dans `~/public_html/`, export Expo dans `~/public_html/mobile/`, module image dans `~/studioapi/app/images.py`, puis redémarrage Passenger. Les contrôles HTTP confirment `/tarifs/` et `/mobile/nouvelle/` en 200, et `/api/sante` en bonne santé. L'accueil et le bouton de la photo offerte ont été vérifiés dans un navigateur isolé ; le bouton ouvre bien la page de connexion avec `suite=photo`. L'aperçu mobile ouvre son formulaire de connexion sur l'écran d'import direct. La recette API isolée passe 91 tests ; le build Next, l'export Expo, le lint web et le contrôle TypeScript mobile passent. Les quatre avertissements lint sur les `<img>` de l'atelier étaient déjà présents.

L'état fournisseur reste inchangé : `/api/sante` annonce `retouche_disponible=false` et `paiement_disponible=false`. Le dernier appel de contrôle OpenAI avait répondu `credit_balance_exhausted` ; aucune retouche réelle n'a pu être validée. Stripe n'a toujours pas les clés nécessaires à l'encaissement. Ni génération payante ni paiement client n'a été lancé lors de cette publication. Avant ouverture aux clients, il faut recharger le solde API OpenAI, faire une retouche de recette réelle avec contrôle qualité, configurer Stripe et tester un paiement de bout en bout. Le moteur vidéo reste fermé.
